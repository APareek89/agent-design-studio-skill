# Tool catalog by capability

Starting points for the `tooling` cards in the Stack and permissions step. Every name here is a candidate from the skill author's knowledge at authoring time, not a verified current fact: features, pricing, regions, licences and even product names change. Before a candidate is named as the choice in a design, check it with the host's web search (primary sources: vendor documentation, pricing pages, regulator or standards text), record the finding in `research.findings`, and cite it from the card. A candidate that could not be checked stays `verified: false`.

Rules that do not change with the tool: code owns money, identity, dates and limits; a tool holds the least privilege its component needs; retrieval stays separate from the authoritative ledger; a model never gains write authority because a framework offers it. Add a tooling card only for a capability the brief actually needs.

## How to fill a tooling card

- `capability`: one phrase from the first column, or a new one when the brief needs it.
- `choice`: the chosen candidate and the reason in one or two sentences.
- `alternatives`: the rejected candidates with the reason each was rejected.
- `candidates`: every candidate considered, with `kind` (managed, open-source, self-hosted, unknown), a one-line `note` on what was checked, `verified` and the `sourceIds` of the research findings that back it.
- `permission`, `blastRadius`, `approvalRule`, `leastPrivilege`: what the tool may touch, as for any framework card.
- `aws`, `gcp`, `azure`, `openSource`: the equivalent option per platform when it matters; empty strings otherwise.
