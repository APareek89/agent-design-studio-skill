Shop support draft desk
The system in one sentence
Sort shop support requests and help staff write replies they check before sending.

Key design calls
Start with review drafts. Rejected: Automatic action. Why: Staff retain every decision.
Use supplied sources. Rejected: Open browsing. Why: Claims need checked evidence.
Code checks hard facts. Rejected: Model authority. Why: Values and access must be repeatable.

Architecture and model budget

F1 - Workflow choice
Choice: A small deterministic state machine with one bounded drafting call.
Rejected: Free tool-using agent; multi-agent chain.
Trade-off: Few states and no operational writes favor a simple flow; more agents add disagreement and latency.

F2 - Permissions and data
Choice: Read-only supplied evidence and local artifact export; no business write credentials.
Rejected: Connect full operational accounts.
Trade-off: A wider connection adds exposure without helping this review-only release.
Access: Separate source read principal from model; source allowlist enforced before retrieval; minimize, redact, expire per approved policy.

F3 - Storage and deployment options
Choice: Choose encrypted existing team storage with access checks and a relational run manifest; verify
environment before purchase.
Rejected: AWS object store plus relational ledger; GCP object store plus relational ledger; Azure object store plus relational ledger;
self-hosted object...
Trade-off: Compare same criteria: scoped reads, region, retention, audit, operations effort and price. Existing team storage wins
provisionally; self-hosting adds operational burden. Retrieval...
Access: Separate source read principal from model; source allowlist enforced before retrieval; minimize, redact, expire per approved policy.
These are reader summaries. Complete choices, alternatives, gates and owners are in PRD.md and design.json.

Measurement and rollout

R1 - Business measure
Measure: Staff active minutes per reviewed reply; weekly sum of active review minutes / number of completed
reviews. Baseline unknown; proposed improvement goal set after baseline.
Signals: Fewer unsupported claims reduces rework; usefulness can lower review effort but must be measured.; No private-data leakage is a
safety guardrail, not a claimed...

R2 - Shadow on historical cases
Phase / owner: shadow / Shop support lead

Gate: Entry: approved scope and lawful sample access. Exit: all release goldens and held-out citation/privacy
checks pass; domain owner signs evidence.

R3 - Assist-only pilot
Phase / owner: assist pilot / Shop support lead

Gate: Entry: shadow exit and H1-H3/H5 verified. Review two weekly cycles, staffed capacity confirmed. Exit: no
safety failures and useful drafts >=H5; owner may extend review-only usage. Scale keeps human review and all...

R4 - Measure review effort
Test: Randomize eligible case families to manual or assistant draft; stratify routine/exception and operator. Same
source family stays in one arm; hide treatment drafts from control. Collect baseline variance of active minutes,
choose minimum useful difference with owner, compute...
Decision gate: Entry uses baseline/power plan, never already-achieved pilot results. Stop for any critical failure.

R5 - Accountable owner and stop plan
Phase / owner: all / Shop support lead

Gate: Lead owns backlog, privacy incident response and release decision; technical owner owns adapters and
evidence receipts. Stop use on safety breach; preserve scoped audit then manual fallback.
These are reader summaries. Complete choices, alternatives, gates and owners are in PRD.md and design.json.
