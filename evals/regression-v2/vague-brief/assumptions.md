Review findings:

- B1 [major, OPEN] components/C4: C4 requires a local artifact receipt before returning ready, while the first explicit receipt creation is in later C5. C4 has no receipt writer/input contract and C5 receives checked rather than the draft body. Specify the actual pre-check artifact writer/read-back, content binding and error response, or move the proof gate after creation, with corresponding workflow and golden updates.
- B2 [major, OPEN] components/C3: C3 output is described only as object/text/claim citations/disagreement/disposition. Citation, claim, evidence, approved manifest, sourceVersion and case record schemas remain prose; C4 claims deterministic allowed-claim validation without a defined supported-claim representation or checking procedure. Define structured field types, required/null rules, citation and fact bindings, and exact error-to-status mappings so implementation does not invent material contracts.
- B3 [major, OPEN] evals/EV7: The stale replacement fixture provides caseRevision=2 and expectedRevision=1 but no persisted current revision or compare-and-swap read result. This also describes a normal next revision from version 1. A valid replacement positive case and an independently stale stored-version case are required; define atomic request revision reservation and final check. EV14 likewise uses sourceVersion="same" rather than an actual frozen manifest.
- B4 [major, OPEN] evals/EV10: EV10 expects REVIEW_OVERDUE from handoffEvent after nine working hours, but W5 is a terminal caller-session return and explicitly does not wait for acknowledgement; acknowledgement occurs outside the tool. No handler/component contract consumes this event or owns a persisted pending list. Specify a separate bounded monitor contract and fixture or scope this as a manual procedure with a manual acceptance test.
- B5 [major, OPEN] evals/EV1: All fourteen goldens were inspected in full. mockSequence entries such as "model -> source-grounded draft" are prose with no actual typed candidate/claim payload, so exact checker behavior requires an implementer-authored model mock. No fixture exercises one read retry then unavailable, revocation after authorized read before output, cancellation during the model call, or two workers racing on one revision. Supply concrete mock responses and event schedules with exact forbidden-effect/receipt assertions; risk links alone do not cover those controls.
- B6 [major, OPEN] evals/EV2: The chosen boundary accepts employee onboarding and explicitly routes customer/vendor/other types as unsupported, but no fixture tests a known unsupported type, mismatched template type, or stale approved template version. EV2 tests unknown type plus scopeConfirmed=false together. Add isolated negatives and a contract mapping unsupported type to a declared intake/evidence state and coordinator-owned handoff.
